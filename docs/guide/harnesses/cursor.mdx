`dist/cursor/` は、このフレームワークが出荷するハーネス配布物の 1 つであり、[Cursor](https://cursor.com) 向けです。1 つのツリーで **Cursor IDE** と **Cursor CLI**（`agent`）の両方をカバーします。どちらも同じ `.cursor/` の探索パスを共有するためです。1 つの決定論的なコアを複数のハーネスへ展開します。エンジン、状態機械、監査ログ、グラフ、スウォーム審判、学習用ゲートはどの配布物でもバイト単位で同一であり、異なるのはシェルだけです。このツリーは `core/` と `harness/cursor/` から `bun scripts/package.ts cursor` で **生成** されます。手作業で編集してはいけません（差分監視により CI が失敗します）。

<a id="layout"></a>
## レイアウト

Cursor は現時点でもっとも「ネイティブ」な移植先です。標準のコア射影をそのまま消費します（`emit.ts` も、ドットディレクトリの分割もありません）。配布物の構成は次のとおりです。

- **`.cursor/`** - フレームワークツリーです。Cursor がネイティブな意味を持つものとして読むのは、いくつかのサブディレクトリだけです: `rules/`（1 つの恒常メソッドポインターと 4 つのフェーズポインター）、`agents/`（14 のペルソナをネイティブサブエージェントとして）、`skills/`（オーケストレーター、ユーティリティのショートカット、生成されたステージランナー）、`hooks.json` + `hooks/`（フック配線とアダプター）、`cli.json`（権限）、`mcp.json`（MCP サーバー。追加する場合）。その隣にあるエンジンディレクトリ（`tools/`、`aidlc-common/`、`knowledge/`、`sensors/`、`scopes/`）は Cursor から見れば単なるデータであり、同じディレクトリを安全に共有できます。
- **`aidlc/`** - ワークスペースシェルです（エンジンが読む、事前構築済みの `aidlc/spaces/default/memory/` メソッドツリー）。`.cursor/` の隣に置かれます。
- **`AGENTS.md`** - Cursor が自動的に読む、プロジェクトルートの環境指示です。

<a id="prerequisites"></a>
## 前提条件

- **Cursor** - IDE、または Cursor CLI（`curl https://cursor.com/install -fsS | bash` でインストールし、`agent` として呼び出します）。どちらもこのインストールの `.cursor/` サーフェスを読みます。cursor-agent 2026.07 で検証済みです。フック（`.cursor/hooks.json`）とスキル（`.cursor/skills/`）は現行系列の機能です。
- **bun** - 他のすべてのハーネスと同じ要件です。すべてのツールとフックが bun 経由で動きます。Cursor が起動するシェルから見える PATH に `bun` が存在する必要があります。
- **名前付きモデルを使うには Cursor の有料プラン** - Free アカウントでは `Auto` しか使えません。ティア付きのペルソナサーフェスは **モデル固定なし** で出荷されます（Cursor では全ティアが null に射影されます。利用できるモデルがプランに依存するためです）。したがってすべてのエージェントがセッションのモデルを継承します。`--model` を渡すヘッドレス CLI 実行には、それを許可するプランが必要です。Bedrock の BYOK は IDE 専用です（Pro では静的キー、Teams では IAM ロール。Cursor のモデル設定のドキュメントで確認したもので、ここでの実機検証はしていません）。CLI は Cursor 自身のバックエンド経由でモデルを利用します。

<a id="install"></a>
## インストール

1. 配布物をプロジェクトへインストールします。

   ```bash
   bun dist/cursor/install.ts your-project
   ```

   インストーラーはコピー全体を事前検査し、プロジェクト所有ファイルとの衝突を拒否し、`.cursor/.gitignore` と既存のメソッドメモリを保持し、`.cursor/hooks.json` と `.cursor/cli.json` を構造的にマージし、既存の `AGENTS.md` と `.gitignore` については置き換えではなく AI-DLC の印を付けたセクションを追加します。フレームワークの所有情報は `.cursor/aidlc-install.json` に記録されます。再実行すると、管理対象ファイルを更新しつつ `aidlc/active-space` と明示的なプラグイン選択・合成済み状態を保持し、削除後に復元されたファイルも含め、変更可能なすべてのルールとペルソナのポインターにそのスペースを再適用します。プラグインが合成したステージファイルは、コントリビューションのサイドカーまたはシームのセンチネルがそのステージを特定できる場合にのみ保持され、インストーラーは保持した管理対象パスをすべて出力します。無関係なコアステージは、通常の受領ハッシュによる衝突・更新処理を通ります。
   `aidlc/` シェルには、エンジンが読む事前構築済みの `aidlc/spaces/default/memory/` メソッドツリーが含まれます。これがないと `/aidlc --doctor` の "workspace shell ready" チェックが失敗します。

2. Cursor IDE でプロジェクトを開き（または、そのディレクトリで `agent` を起動し）、`/aidlc --doctor` を実行してから、`/aidlc` に続けて作りたいものを入力します。ネイティブなユーティリティのショートカットは `/aidlc-status`、`/aidlc-jump --stage <slug>`（または `--phase <name>`）、`/aidlc-scope <name>` です。

<a id="whats-different-on-this-harness"></a>
## このハーネスでの差分

- **質問は番号付きの散文の選択肢として表示されます**（構造化質問ウィジェットはありません）。`[Answer]:` タグを持つ質問ファイルが引き続き正本です。
- **フックは `.cursor/hooks.json` に乗ります。** AIDLC アダプター（`.cursor/hooks/aidlc-cursor-adapter.ts`）が、Cursor の camelCase なフックイベント（`sessionStart`、`sessionEnd`、`beforeSubmitPrompt`、`preToolUse`、`postToolUse`、`postToolUseFailure`、`preCompact`、`stop`）を、バイト共有されたコアのフック本体（bun のサブプロセスとして実行）へ対応付けます。人間のターンごとの人間ターン記録、ツール実行前の状態遷移・レビュアー読み取りスコープ・レビュー凍結・プラン承認の各ガード、書き込み／編集時の監査とセンサー、失敗した Task の帰属クリーンアップ、シェル実行時のステージグラフ再構築、コンパクト化前の状態検証が含まれます。**PreToolUse のガードは**、Cursor の `{"permission":"allow"|"deny"}` という標準出力チャネルで応答し（`deny` には `agent_message` を添えられます）、`failClosed: true` を登録します。標準出力が空の場合は不正な JSON となるため IDE は呼び出しをブロックします。不正な入力、ガードの欠落、ガードのクラッシュも同様に操作を拒否します。Cursor はシェルツールを `Shell` と呼びます。アダプターはこれをコアフックの `Bash` に対応付けます。Cursor が第一級のツールとして持つ `Delete`（このハーネス固有で、他ではすべて削除はシェル経由）は、レビュアースコープのガードに対して書き込みとして提示されます。そのためユニット単位のスコープを持つレビュアーが、隣のユニットの成果物を削除することはできません。シェルのペイロードにネストした `cwd`／`working_directory` フィールドは共有のガード契約へ引き上げられるため、相対パスの読み書きは Cursor が実際に実行する場所を基準に検査されます。
- **転送ループの強制は勧告的です。** Cursor の `stop` フックは停止を拒否できないため、コアの stop フックが `block` を返した場合、アダプターは代わりに追加の催促を提示します（opencode と同じ姿勢です）。ホスト側の `loop_limit` は Cursor 既定の 5 ではなく 10 で、コアの自律実行時の「進捗なし」上限である 8 をカバーします。実際の規律はコンダクタースキルの転送ループが担います。
- **実際のセッション終了の契機が存在します**（Codex とは異なります）。`sessionEnd` が発火するため、`SESSION_ENDED` の監査イベントが記録されます。コンパクト化前の検証（`preCompact`）も発火します。
- **ペルソナはネイティブサブエージェントです。** `.cursor/agents/` にある 14 のペルソナ `.md` ファイルは、フロントマターの `name` で発見されます。コンダクターはほとんどのステージでそれらをインラインに採用し、2 つのサブエージェントステージ（2.1 リバースエンジニアリング、3.5 コード生成）では `task` ツールで委譲します。ワーカーエージェントは `task` ツールを持たないため、委譲先がさらに委譲することはできません。
- **サブエージェントの同一性は再構成されます。** Cursor はフックのペイロードにサブエージェント単位の同一性を出しません（`subagentStart`／`subagentStop` イベントは文書化されていますが CLI では決して発火しません）。そのためアダプターは、`aidlc/.aidlc-cursor-subagents/` 配下に保護されたプロジェクトローカルの実行時台帳を維持します。トップレベルの会話は `sessionStart`／`beforeSubmitPrompt` で自身を登録し（サブエージェントの会話はどちらのイベントも受け取りません）、Task のスポーンごとにそのエージェントを記録し、レビュアー読み取りスコープの強制は、トップレベルセッションとして登録されていない会話からの呼び出しに帰属を与えます。親の次の同期的な Task ディスパッチは、直前の記録を退役させてログに残します（Cursor CLI は Task の `postToolUse` を出しません）。親をまたぐ本当の曖昧さは、レビュアーが有効な間は常に保守的に扱われるため、レビュアースコープの強制を無効化することはできません。委譲されたツールは、祖先の削除や引用符なしのシェルグロブ／文字クラスのパスを通じても、台帳やディスパッチ記録へアクセスできません。レビュアーのディスパッチが有効な間に帰属情報の保存先が失われたり読めなくなったりした場合は、レビュアーの強制を逃れるのではなくフェイルクローズします。レビュー委譲先は通常の Shell コマンドを使えますが、汎用インタープリターと動的なコマンド評価は拒否されます。Cursor のネイティブな読み取り・検索ツールを使い、実行を伴う調査は親の会話に任せてください。
- **生成されたステージランナーとスコープランナーは明示呼び出し専用です。** Cursor では、プラグインのランナーも含め、生成されたランナースキルに `disable-model-invocation: true` が付きます。そのため通常のコーディング用プロンプトが、状態を変更するワークフローのショートカットを自動起動することはありません。
- **ユーティリティのショートカットはネイティブスキルです。** `/aidlc-status`、`/aidlc-jump`、`/aidlc-scope` は、2 つ目のエンジン経路を作ることなくスラッシュメニューでの発見性を高めます。いずれも `disable-model-invocation: true` を持ち、Cursor は利用者が選んだときにだけ呼び出します。レガシーな `.cursor/commands/` サーフェスは出荷しません。
- **メソッドのルールは読み取り指示であり、インポートではありません。** Cursor のルールは `@` インポート行を展開しません。`.cursor/rules/aidlc.mdc` は常時適用され、アクティブなスペースの org／team／project ファイルを指します。4 つの `.cursor/rules/aidlc-phase-*.mdc` ルールはエージェントが判断するもので、関連する場合にのみ対応するフェーズファイルを指します（cursor-agent で実機検証済み: フェーズを含意するプロンプトでは対応するフェーズルールだけが読み込まれ、無関係なプロンプトでは 1 つも読み込まれません）。`sessionStart` フックは、これとは別に実行中のワークフロー文脈を注入します。`/aidlc space <name>` は 5 つのルールファイルすべてをその場で指し直します。
- **構築フェーズのスウォームは task ツールのファンアウトとしてのみ動きます**（`AIDLC_USE_SWARM=1` は明示的に何もしません。Workflow ツールが存在しないためです）。
- **ステータスラインとウェルカムメッセージはありません** - `/aidlc-status`（または `/aidlc --status`）とゲートでの進捗表示を使ってください。
- **タブ補完はこのインストールの影響を受けません** - 設定にかかわらず Cursor 自身のモデルで動きます。
- **権限**: `.cursor/cli.json` は `Shell(bun)` のみを事前承認します（プロジェクトレベルの `cli.json` は権限だけを扱います）。それ以外のシェルコマンドは、あなたの Cursor の承認設定に従います。
- **MCP サーバー**: 何も出荷しません。必要なら `.cursor/mcp.json` に自分で設定してください。
- **ヘッドレスな `agent -p` 実行では承認ゲートを通過できません。** 人間の在席を示す記録は `beforeSubmitPrompt` に乗りますが、Cursor はこれを対話的な送信でのみ発火させます（cursor-agent 2026.07 で検証済み）。したがって print モードの実行では `HUMAN_TURN` が記録されず、ゲートのあるステージは設計どおり承認を拒否します。無人のモデルが自分の作業を自分で承認してしまうことを防ぐためです。ヘッドレスモードは読み取り専用のユーティリティ（`--status`、`--doctor`、`--version`）と、自律的な構築フェーズ（ゲートに人間が介在しないため適用除外）に使ってください。ゲートを伴うワークフローは対話的な Cursor セッションで実行します。これは Cursor の制限ではなくフレームワークの在席ゲートの性質であり、どのハーネスでも在席は人間のプロンプトイベントから記録されます。

<a id="verifying-an-install"></a>
## インストールの検証

```bash
bun .cursor/tools/aidlc-utility.ts doctor        # all checks pass on a fresh copy
agent -p "/aidlc --status" --output-format text --trust   # /aidlc --status through the CLI
```

診断ツールの Cursor 固有チェックは次のとおりです: `.cursor/hooks.json` のフック配線、`.cursor/cli.json` における `Shell(bun)` 権限の事前承認、`.cursor/rules/aidlc.mdc` の恒常ルール、そして 4 つのフェーズルールポインターすべて。

:::note
**スクリプト作成時の落とし穴: Cursor CLI は常に 0 で終了します。** ヘッドレスな `agent -p "<prompt>" --output-format text --trust` は、実行が失敗した場合でも終了コード 0 を返します。そのため CI のチェックは、終了ステータスではなく必ず出力テキストに対して判定してください。名前付きモデル（`--model`）には有料プランが必要です。ない場合は `Auto` を使ってください。
:::
